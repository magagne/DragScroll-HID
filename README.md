# Corne-Ploopy-Bridge

A small host-side bridge connecting a **Corne / ZMK keyboard** to a
**Ploopy pointing device**.

The bridge receives custom **Raw HID events** from the keyboard and
forwards the corresponding commands to the Ploopy.

The main use case is **DRAG_SCROLL**.

## Architecture

    Corne / ZMK
         │
         ▼
    Raw HID event
         │
         ▼
    Corne-Ploopy-Bridge
         │
         ▼
    Ploopy

## DRAG_SCROLL

`DRAG_SCROLL` is a custom pointing event generated by the Corne / ZMK
firmware.

The keyboard sends the event through Raw HID. The bridge receives the
event on the host and forwards the corresponding command to the Ploopy.

The event flow is:

    Corne / ZMK
         │
         │ DRAG_SCROLL
         ▼
      Raw HID
         │
         ▼
    Corne-Ploopy-Bridge
         │
         │ Ploopy command
         ▼
       Ploopy

This keeps the responsibilities separate:

- **Corne / ZMK** generates the event.
- **Raw HID** transports the event.
- **Corne-Ploopy-Bridge** receives and forwards it.
- **Ploopy** performs the resulting pointing or scrolling behavior.

## Raw HID

The bridge listens for the HID interface used for communication with the
keyboard.

The expected interface is identified by:

    Usage Page : 0xFF60
    Usage      : 0x0061

The bridge does not depend on a specific keyboard VID/PID.

This allows compatible keyboards exposing the expected Raw HID interface
to be used without changing the bridge configuration.

## Device Handling

The bridge is designed to handle the keyboard being connected or
disconnected while the bridge is running.

It supports:

- device discovery
- device connection
- device disconnection
- hot-plug
- hot-unplug
- reconnection

The bridge can remain running while the keyboard is temporarily
unavailable.

## Bridge Implementation

The core bridge implementation is:

    src/
    └── bridge.py

The bridge is a host-side component. It receives events from the keyboard
through Raw HID and communicates with the Ploopy.

The keyboard firmware and Ploopy firmware remain independent from the
host-side bridge.

## Platform Startup

Platform-specific process startup is kept separate from the core bridge.

The core event flow remains:

    Keyboard / ZMK
          │
          │ Raw HID
          ▼
        Bridge
          │
          │ Ploopy command
          ▼
        Ploopy

The operating system only provides the mechanism used to start and keep
the bridge process running.

### macOS

The macOS LaunchAgent implementation is located under:

    platform/mac/launchagent/
    ├── install.sh
    └── com.corne-ploopy-bridge.plist

The normal way to install and start the Agent is:

    ./platform/mac/launchagent/install.sh

The LaunchAgent service identifier is:

    com.corne-ploopy-bridge

To verify that the Agent is loaded:

    launchctl print gui/$(id -u)/com.corne-ploopy-bridge

The detailed macOS LaunchAgent documentation is:

    doc/mac/launchagent.md

### Windows

The bridge architecture is not tied to macOS.

A Windows startup mechanism can be provided independently from the core
bridge.

A future PowerShell launcher can be used with Windows Task Scheduler or
another scheduled-start mechanism.

The platform startup layer should remain separate from the bridge logic.

## Debugging

The bridge provides a debug mode for development and troubleshooting:

    --debug

Debug mode can be used to inspect device discovery, connection state,
and bridge activity.

Normal automatic operation should use the platform startup mechanism
rather than manually launching the Python implementation.

## Design Goal

The bridge is intentionally small and focused on transporting custom
pointing-related events between the keyboard and the Ploopy.

The keyboard decides **what event to generate**.

Raw HID carries the event to the host.

The bridge decides **how to forward the event**.

The Ploopy performs the resulting pointing behavior.

Platform-specific startup mechanisms remain outside this core event flow.
