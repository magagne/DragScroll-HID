# DragScroll-HID

A small host-side HID bridge for transporting custom **DRAG_SCROLL**
commands from keyboard firmware to a compatible pointing device.

The current implementation is designed around:

- **QMK / VIAL** keyboard firmware
- **ZMK** keyboard firmware
- **Raw HID** transport
- **Ploopy** pointing devices

The main purpose of the project is to provide a clean host-side transport
layer for **DRAG_SCROLL**.

The bridge itself does not implement the drag-scroll behavior. The keyboard
firmware generates the event, the bridge transports it, and the pointing
device performs the resulting behavior.

## Architecture

    QMK / ZMK

         │

         │ DRAG_SCROLL

         ▼

      Raw HID

         │

         ▼

    DragScroll-HID

         │

         │ HID command

         ▼

      Ploopy

This keeps the responsibilities separate:

- **QMK / ZMK** generates the DRAG_SCROLL event.
- **Raw HID** transports the event to the host.
- **DragScroll-HID** receives the event and forwards the corresponding
  command.
- **Ploopy** performs the resulting pointing or scrolling behavior.

## DRAG_SCROLL

`DRAG_SCROLL` is a custom pointing event generated by the keyboard firmware.

The keyboard sends the event through Raw HID. The host-side
DragScroll-HID process receives the event and sends the corresponding
command to the Ploopy.

The current protocol uses:

    'S'  → DRAG_SCROLL ON

    's'  → DRAG_SCROLL OFF

On the Ploopy side, these commands are handled through the VIA command hook
and control the existing Ploopy drag-scroll engine.

## QMK / VIAL

The QMK implementation contains the custom DRAG_SCROLL module separately
from the normal keyboard firmware:

    Crkbd-VIAL
      └── modules/drag_scroll/
            ├── drag_scroll.c
            └── drag_scroll.h

The module generates the DRAG_SCROLL state changes and sends the corresponding
Raw HID commands.

The keyboard-specific implementation therefore remains isolated from the
normal QMK keyboard firmware.

## ZMK

The same host-side protocol can also be used from the ZMK keyboard
implementation.

ZMK generates the DRAG_SCROLL state and sends the corresponding HID command
to DragScroll-HID.

The host bridge therefore does not need to know whether the originating
keyboard firmware is QMK or ZMK.

## Ploopy Side

The Ploopy firmware is maintained separately in the **Ploopy-VIA** project.

The Nano 2 VIA keymap contains the Raw HID command handling:

    Ploopy-VIA
      └── via_scrolllock/
            ├── keymap.c
            └── rules.mk

The keymap implements `via_command_kb()` and handles:

    'S' → is_drag_scroll = true

    's' → is_drag_scroll = false

The Ploopy firmware already contains the underlying drag-scroll engine.
The custom VIA integration only provides the HID-controlled state change.

## Scroll Lock LED

The Ploopy implementation also integrates the DRAG_SCROLL state with the
Ploopy's existing Scroll Lock behavior.

The Ploopy firmware maintains:

    is_drag_scroll

and synchronizes it with the Scroll Lock LED state where appropriate.

This means the physical Scroll Lock state and the drag-scroll state can be
represented consistently by the Ploopy firmware.

The custom integration remains isolated from the normal Ploopy firmware
through the keymap-specific implementation.

## Raw HID

DragScroll-HID communicates through the Raw HID interface exposed by the
keyboard.

The expected HID interface is:

    Usage Page : 0xFF60

    Usage      : 0x0061

The bridge does not depend on a specific keyboard VID/PID.

Any compatible keyboard exposing the expected Raw HID interface can
therefore be used without changing the bridge configuration.

## Device Handling

The bridge is designed to handle keyboard connection changes while it is
running.

It supports:

- device discovery
- device connection
- device disconnection
- hot-plug
- hot-unplug
- reconnection

The bridge can remain running while the keyboard is temporarily
unavailable.

## Implementation

The core host-side implementation is:

    src/
    └── drag_scroll_hid.py

The implementation is intentionally small.

The keyboard firmware and Ploopy firmware remain independent from the
host-side bridge.

## Platform Startup

Platform-specific process startup is kept separate from the core HID
implementation.

The core event flow remains:

    QMK / ZMK

          │

          │ Raw HID

          ▼

    DragScroll-HID

          │

          │ HID command

          ▼

       Ploopy

The operating system only provides the mechanism used to start and keep
the DragScroll-HID process running.

### macOS

The macOS LaunchAgent implementation is located under:

    platform/mac/launchagent/

    ├── install.sh
    └── com.dragscroll-hid.plist

The normal way to install and start the LaunchAgent is:

    ./platform/mac/launchagent/install.sh

The LaunchAgent service identifier is:

    com.dragscroll-hid

To verify that the LaunchAgent is loaded:

    launchctl print gui/$(id -u)/com.dragscroll-hid

The LaunchAgent redirects normal output and errors to:

    dragscroll-hid.log
    dragscroll-hid-error.log

Detailed macOS LaunchAgent documentation is available in:

    doc/mac/launchagent.md

### Windows

The bridge architecture is not tied to macOS.

A Windows startup mechanism can be provided independently from the core
DragScroll-HID implementation.

A future PowerShell launcher can be used with Windows Task Scheduler or
another scheduled-start mechanism.

The platform startup layer should remain separate from the HID logic.

## Debugging

The bridge provides a debug mode for development and troubleshooting:

    --debug

Debug mode can be used to inspect device discovery, connection state,
and HID activity.

Normal automatic operation should use the platform startup mechanism
rather than manually launching the Python implementation.

## Complete Event Flow

The complete system can be viewed as:

    KEYBOARD SIDE

    QMK / VIAL
      └── modules/drag_scroll/
            ├── drag_scroll.c
            └── drag_scroll.h
                    │
                    │ Raw HID 'S' / 's'
                    ▼
             DragScroll-HID
                    │
                    │ HID command
                    ▼
    PLOOPY SIDE

    Ploopy-VIA
      └── via_scrolllock/keymap.c
            │
            └── via_command_kb()
                    │
                    └── is_drag_scroll
                            │
                            ▼
                    Ploopy's existing
                    drag-scroll engine

The bridge is therefore a transport component between the keyboard-side
DRAG_SCROLL implementation and the pointing-device-side drag-scroll
implementation.

## Design Goal

DragScroll-HID is intentionally small and focused.

The keyboard decides **when DRAG_SCROLL should be enabled or disabled**.

Raw HID carries that state change to the host.

DragScroll-HID transports the command.

The Ploopy firmware applies the state to its existing drag-scroll engine.

This separation allows QMK, ZMK, the host bridge, and the Ploopy firmware
to remain independently maintained.
